# SBA Modeling Requirements

The canonical requirements are maintained in [documents/sba_modeling_requirements.md](../documents/sba_modeling_requirements.md).

## Prologue: feature selection and modeling approach

Feature selection is a first-class modeling decision in this workflow, not a cosmetic preprocessing step. The SBA data contains many correlated, sparse, and potentially leakage-prone candidate fields, so model capacity alone should not determine the feature set. A compact, externally screened feature contract reduces instability, limits target-encoded categorical complexity, makes the pipeline easier to audit, and gives threshold tuning a stable input surface.

This project uses [imbalanced_feature_screener](https://github.com/rajivsam/imbalanced_feature_screener) as the reference tool for ranking features under class imbalance. The screener combines multiple complementary signals and is especially useful here because standard in-model importance from one fitted classifier can overstate unstable predictors or be distorted by the low prevalence of distressed loans.

The current baseline is intentionally fixed at the five highest-ranked features in the screener report:

1. `bankname`
2. `bankcity`
3. `initialinterestrate`
4. `bankstreet`
5. `terminmonths`

The five-feature constraint is a controlled current baseline rather than a permanent assumption. The feature selection contract must remain parameterized conceptually:

- the number of features to retain (`top_k`);
- the ordered identities of retained features;
- the screener ranking and configuration used to produce them;
- the feature-screen version or source reference;

Future experiments may vary `top_k` or compare alternative ranked subsets, but each run must record the selected feature list and evaluate it against the same frozen train/validation/test contract. The current five-feature model is retained because reducing the prior broader set materially improved held-out ranking and operating-point performance. Features must not be added merely because they are available; a broader set should replace the baseline only when the screener-supported result is independently better on validation and remains stable on test.

This approach separates responsibilities. The screener determines a compact, defensible candidate signal set; the modeling notebook fits and calibrates candidate classifiers on training data; validation builds gains/lift curves and freezes the review cutoff; and test is evaluated once for out-of-sample reporting. Neither validation nor test data may be used to reshape the feature set after reviewing model performance.

## Notebook-first modeling requirements

This project now uses a notebook-first workflow for modeling. The notebook `notebooks/sba_modeling.ipynb` is the implementation source of truth and reads the numeric model-ready dataset generated by `notebooks/sba_featurization.ipynb`.

The modeling notebook must:

- load `data/featurization/model_ready_numeric_data.csv`;
- require and record exactly the current five-feature baseline, while preserving feature count and membership as explicit experiment parameters;
- use `dataset_partition` as the authoritative split source;
- train candidate models only on the `train` rows;
- calibrate the first-stage classifier with isotonic regression;
- retain a recall-maximizing threshold as a validation diagnostic;
- score and rank every validation row by calibrated default probability;
- build a cumulative gains and lift table by review decile;
- select the review percentile at the elbow of the cumulative gains curve, defined as the largest positive distance above the random-selection baseline;
- freeze both that percentile and its boundary probability score before evaluation;
- report tie effects when a shared calibrated score makes the realized probability-threshold review rate larger than the selected percentile;
- evaluate the frozen calibrated model and frozen threshold on the `test` rows;
- report out-of-sample performance without re-splitting the data;
- preserve compatibility with the repository CLI utility layer for later automation.

The CLI package remains a wrapper or compatibility layer for the same logic, not the primary driver of the workflow.
