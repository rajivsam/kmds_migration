# Test / Train / Validation / Active Partition Rework

## Goal

Use a single, canonical dataset partition column in the featurized model-ready file so that both the featurization pipeline and the modeling pipeline read the exact same train/validation/test/active assignments. This avoids re-splitting inside the modeling package and prevents leakage caused by inconsistent partitions.

## Required contract

The model-ready dataset generated by the featurization pipeline must include a column named `dataset_partition`.

Allowed values:
- `train`
- `validation`
- `test`
- `active`

The value semantics are:
- `train`: rows used to fit all estimators and transformers
- `validation`: rows used for model selection, threshold tuning, and calibration comparison
- `test`: rows held out for final, frozen performance reporting only
- `active`: unlabeled or not-yet-scored rows reserved for downstream scoring only

The canonical rule is:
- no model fitting on validation, test, or active rows
- no random re-splitting inside the modeling package
- the partition assignment is authoritative and generated once during featurization

## Featurization package requirements

The featurization package must generate the `dataset_partition` column on the output file that becomes the model-ready source used by modeling.

### Required behavior
1. Start from the filtered modeling universe, where `loan_status_r` is limited to the relevant classes for supervised modeling.
2. Apply a deterministic split to the labeled sample before target encoding and other fit-based feature engineering.
3. Write the resulting partition labels to a column named `dataset_partition`.
4. Use the labeled universe only for train / validation / test assignment.
5. Keep active loans in the final model-ready dataset with `dataset_partition = "active"` and retain them for scoring only.
6. Ensure the same row-level assignment is preserved through later featurization steps.

### Recommended split policy
- Use a fixed random seed (for example `random_state=42`) for reproducibility.
- Use stratification on the target column for the labeled classes.
- Keep the label logic consistent with the business rules:
  - `loan_status_r == -1` => active
  - `loan_status_r in [0, 1]` => labeled rows eligible for train / validation / test
- The labeled set should be partitioned into three buckets:
  - `train`
  - `validation`
  - `test`
- If a project chooses to omit a dedicated test set initially, the modeling contract may begin with `train` and `validation` only, but the final intended setup is `train`, `validation`, and `test`.

### Leakage protection in featurization
The featurization package must enforce this rule:
- target encoders, cluster fitting, and other fit-based transformations are trained only on the `train` partition
- validation and test partitions are not used to fit the transformation or encoding parameters
- downstream model-ready output may carry validation/test rows, but they must remain untouched by fitting logic

## Modeling package requirements

The modeling package must read the model-ready file and use `dataset_partition` as the single source of truth. It must not do a second random train/test split.

### Required behavior
1. Read `data/featurization/model_ready_numeric_data.csv`.
2. Require the column `dataset_partition` to exist.
3. Use these filters:
   - `train_df = df[df["dataset_partition"] == "train"].copy()`
   - `validation_df = df[df["dataset_partition"] == "validation"].copy()`
   - `test_df = df[df["dataset_partition"] == "test"].copy()`
   - `active_df = df[df["dataset_partition"] == "active"].copy()`
4. Keep `loan_status_r` == -1 only in `active_df`.
5. Use only labeled rows for training and evaluation:
   - `loan_status_r` in {0, 1}
6. Fit transformers, encoders, and clustering logic only on `train_df`.
7. Apply the learned transform to `validation_df` and `test_df` only.
8. Select threshold and compare candidate models using `validation_df` only.
9. Freeze the chosen model and threshold before reporting final performance on `test_df`.
10. Use `active_df` only for scoring and downstream production workflows.

### No hidden re-splitting
The modeling package must reject or bypass any logic that performs a second random split from the same dataset unless the partition column is absent and an explicit backward-compatibility fallback is intentionally enabled.

The allowed fallback behavior is:
- if `dataset_partition` is missing, the modeling package may fall back to a legacy split
- but this fallback must be treated as compatibility-only and should log or warn that the partition column is absent
- modern workflow and default behavior must rely solely on `dataset_partition`

## Recommended implementation decision

The cleanest and safest design is:
- featurization owns the partition assignment
- modeling owns the application of the partition assignment
- there is one partition column and one truth source

This is better than doing a second split in modeling because it makes the dataset lineage explicit and auditable.

## Data contract for final model-ready file

The final `model_ready_numeric_data.csv` file should include all of the following conceptually:
- feature columns produced by the featurization pipeline
- the target column `loan_status_r`
- the split column `dataset_partition`
- optionally any retained index or record identifier columns used for traceability

The final row-level contract should be:
- each row is assigned exactly one partition
- each partition has a single meaning
- no row is assigned to multiple partitions
- training, validation, test, and active partitions are mutually exclusive

## Summary

The objective is to move to a single-partition data contract:
- a row is either `train`, `validation`, `test`, or `active`
- the partition is assigned during featurization
- modeling uses that exact assignment without re-splitting
- validation is for threshold tuning and model comparison
- test is for final performance reporting
- active is for scoring only

This gives the project an unambiguous, leakage-safe, reproducible training pipeline.
